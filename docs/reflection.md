Reflection - NetMessenger

During the NetMessenger project, I used AI tools mainly as a development and troubleshooting aid. I used ChatGPT to help me understand the assignment requirements, plan the implementation phases, write and explain test commands, and troubleshoot issues during testing. I also used the AI guidance to understand how the server, client, TCP framing, threads, rooms and file transfer should work. However, I did not treat the generated output as automatically correct. I compiled the program and ran the required tests myself and compared the actual behaviour with the protocol requirements.

One thing AI did well was break a large networking assignment into smaller phases. This made it easier to implement and test registration, messaging, rooms and file transfer separately. The testing guidance was also useful because it gave me practical ways to verify behaviours such as partial commands, multiple commands in one TCP receive, exact file-byte handling, malformed input and unexpected client disconnections. For example, the partial-line test helped me understand why `REGISTER fr` cannot be processed until the remaining `amer\n` arrives.

There were also areas where I needed to verify the suggestions myself. I did not assume that an expected output shown by AI would automatically match my implementation. I ran the commands against my actual server and checked the results. I also verified file transfer using `cmp` and `sha256sum` instead of only trusting the displayed success message. This helped me identify the difference between an implementation that looks correct and one that actually behaves correctly.

I changed or rejected suggestions when they did not match my implementation or the assignment requirements. I kept the required personalised port, NID and storage path, and adjusted test commands to match my actual executable and project names. I also used incremental commits instead of treating the project as one large code change because the assignment required process evidence.

The most important thing I learned was that TCP is a byte stream and does not provide application-level message boundaries. Therefore, command framing has to be implemented by the application. I also learned why `send()` may send fewer bytes than requested, why `recv()` returning zero indicates that the peer has closed the connection, and why shared user and room state needs protection with a mutex when multiple client threads access it. File transfer also showed me that command data and binary file data must be handled separately and that the server must consume exactly the announced number of bytes. Finally, testing unexpected disconnects helped me understand why robust servers must handle clients disappearing without sending `QUIT`.
